# NeuroCAD — VeriCodeGen 2026 Successor Protocol

**Status:** PRE-OUTCOME PROTOCOL — PLANNED, NOT EXECUTED  
**Frozen:** 2026-08-30  
**Purpose:** determine whether a structured specification + deterministic compiler/verifier path improves verifiable CAD-code generation over matched direct code generation.

## Scientific boundary

The historical NeuroCAD typed-parser causal/mechanism claim remains falsified. Engineering improvements to the parser/compiler do not rescue that result.

This document defines a **new successor hypothesis**. No result from this protocol may be back-propagated into the historical claim.

## Research question

Under the same language model, task prompts, decoding budget, retry budget, and evaluation suite, does forcing generation through a typed intermediate CAD specification followed by deterministic NeuroCAD compilation/validation reduce invalid or hard-constraint-violating outputs relative to direct OpenSCAD generation?

## Hypothesis

The structured-specification arm will improve **hard verifiability** (compile validity + objectively checkable constraint satisfaction) without an unacceptable semantic-quality or cost penalty.

## Falsifier

The successor hypothesis is falsified for the tested setting if any of the following holds on the frozen primary benchmark:

1. the structured arm does not improve the predeclared hard-verifiability endpoint over matched direct generation;
2. any apparent gain disappears after equalizing retries/token budget and applying the same independent verifier;
3. the structured arm improves syntactic validity while materially degrading semantic task satisfaction;
4. gains are confined to templates already encoded by NeuroCAD and disappear on compositional/OOD prompts;
5. verifier errors or path-specific evaluation advantages explain the result.

## Arms

### A — Direct generation control

The chosen language model receives the natural-language task and produces OpenSCAD directly.

### B — Structured NeuroCAD path

The **same model** receives the same task and produces a typed, schema-constrained CAD specification. NeuroCAD deterministically validates/compiles that specification to OpenSCAD.

The two arms must use the same:

- provider/model/version;
- system-level task information as closely as the formats permit;
- natural-language user task;
- maximum generation budget;
- temperature/top-p policy;
- retry count;
- tool access other than the treatment-defining structured compiler step;
- benchmark examples;
- downstream independent verification.

Any unavoidable prompt-length or schema overhead must be reported explicitly.

## Frozen benchmark design

Target **120 tasks**, authored/frozen before model execution:

- 40 in-distribution primitive/parametric tasks;
- 40 compositional tasks requiring multiple primitives/relations;
- 40 OOD/ambiguity/constraint-stress tasks.

The benchmark must not be generated by the evaluated model after the model/version is selected.

Each task record must contain:

- prompt ID;
- prompt text;
- task family;
- required primitive/object relations;
- numerical constraints and tolerances where applicable;
- expected compile property;
- machine-checkable properties;
- human-judged semantic rubric for properties that cannot be checked automatically.

A held-out benchmark hash must be recorded before first model call.

## Primary endpoint

**Hard Verifiability Rate (HVR)** per task:

A trial scores 1 only if:

1. output compiles/validates;
2. all predeclared machine-checkable hard constraints pass under the independent verifier;
3. no forbidden repair outside the frozen retry policy is used.

Report paired arm difference in HVR with confidence interval and an exact/paired test suitable for binary paired outcomes.

## Secondary endpoints

- raw compile/parse success;
- machine-checkable constraint satisfaction rate;
- semantic task satisfaction under blinded rubric;
- compositional/OOD HVR separately;
- number of retries;
- generated tokens;
- wall-clock latency;
- estimated API cost;
- verifier false-positive/false-negative rate on a manually audited subset;
- failure taxonomy.

Secondary endpoints do not override a failed primary endpoint.

## Repeated trials

For stochastic generation, run at least **5 predeclared decoding seeds per task/arm** if budget permits. If budget forces fewer trials, freeze the reduced trial count before any benchmark outcome is inspected and label the study exploratory.

Do not select or drop seeds after seeing performance.

## Independent verifier requirement

The evaluation path must not reward the structured arm merely because it uses NeuroCAD-internal state.

Where feasible, both arms are evaluated from their final OpenSCAD/geometry artifact using an independent shared verifier.

Verifier development must include deliberately valid and invalid fixtures and measure false acceptance/rejection before the main benchmark is opened.

## Leakage controls

Before execution:

- freeze benchmark and SHA-256 manifest;
- separate benchmark-authoring data from evaluated tasks;
- identify any examples/templates already present in repository docs/tests;
- mark near-duplicates;
- keep development prompts separate from final benchmark;
- do not tune the treatment after inspecting held-out failures.

## Retry policy

Freeze one policy for both arms before execution, e.g. a maximum number of generation attempts with no human correction. If structured validation exposes an error message to the model, the direct arm must receive an information-matched compiler/verifier error where technically possible, or the asymmetry must be treated as a separate intervention rather than bundled into the main comparison.

## Ablations

At minimum, if the primary study is promising:

1. schema constraint removed but compiler retained;
2. validation removed but typed intermediate retained;
3. deterministic compiler without model-facing verifier feedback;
4. direct generation + equal verifier feedback;
5. template-seen vs compositional/OOD subsets.

The goal is to isolate what causes any gain.

## Statistical analysis

Predeclare before execution:

- paired unit: task × decoding seed;
- primary binary endpoint and paired comparison;
- confidence interval method;
- multiplicity treatment for secondary hypotheses;
- policy for failed/time-out trials (count as failures for the relevant validity endpoint unless the protocol specifies otherwise before execution).

Report effect sizes and uncertainty, not only p-values.

## Failure taxonomy

Every failed trial should be assigned, without deleting raw outputs, to one or more categories such as:

- syntax/compile failure;
- unsupported operation;
- missing required object;
- wrong dimension/unit;
- spatial-relation violation;
- disconnected/intersecting geometry when forbidden;
- semantic misinterpretation;
- verifier ambiguity/error;
- timeout/retry exhaustion.

## Execution stages

### Stage 0 — verifier tests
No model/API calls. Build and test shared verification fixtures.

### Stage 1 — tiny development smoke test
Use development prompts only. Confirm both arms, logging, retry accounting, and verifier plumbing work.

### Stage 2 — frozen pilot
Open a small predeclared subset only to estimate runtime/cost and detect implementation defects. Do not tune scientific decision thresholds on it.

### Stage 3 — full frozen benchmark
Run all authorized arm/task/seed cells and retain raw outputs.

### Stage 4 — ablations
Only after primary matrix is complete.

### Stage 5 — clean reproduction
Re-run a predeclared subset from a fresh environment and regenerate paper tables directly from retained logs.

## Required provenance

For every model call or generated output record:

- git commit;
- benchmark manifest hash;
- exact provider/model identifier;
- date/time;
- decoding parameters;
- prompt/template version hash;
- seed if exposed/controlled;
- retry index;
- raw response;
- final artifact hash;
- verifier version/hash;
- runtime and cost where available.

Never commit API credentials.

## Venue/claim gate

This protocol is motivated by verifiable code/specification generation, but venue fit does not make the study valid.

A VeriCodeGen submission should proceed only if:

- benchmark and verifier are frozen before outcomes;
- the matched direct-generation control is complete;
- the primary result is reproducible;
- verifier bias has been audited;
- compositional/OOD results are reported;
- failure modes and negative evidence are retained;
- the paper accurately distinguishes the new successor study from the falsified historical typed-parser claim.

Otherwise mark NeuroCAD **REDESIGN / NOT SUBMISSION READY**.

## Authorization state

**No main benchmark or paid model run is authorized by this document alone.**

Next admissible implementation work is Stage 0: shared verifier fixtures + benchmark schema, followed by a development-only smoke path. Any external model/API execution requires an explicit configured provider and a frozen cost/run manifest.
